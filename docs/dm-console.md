# Minimal DM console (ENG-9)

Sign in through Discord OAuth as the configured campaign DM. The console's
`/dashboard`, `/clocks`, `/characters`, `/quests`, `/ticks/:id/review`,
`/ticks/history`, and `/ticks/:id/history` routes share the authenticated
LiveView session. HTTP/mounts, navigation parameters, and every event recheck the
server session and current DM configuration. Session revocation/expiry redirects
all console views to login. Campaign and actor IDs come from authenticated scope,
never form fields.

## Run a world-only turn

1. **Clocks:** create clocks with 4/6/8 segments, signed background rates,
   public/known/hidden visibility, and optional paused state. Add/remove typed
   on-fill triggers: public world news, private DM notification, or start another
   clock. Starting unpauses the target; it does not run another background rate.
   Public trigger news must not contain secrets, even on hidden clocks.
2. Edit or adjust live inputs before closing. Pause/resume, reset, and racing-pair
   controls call the shared clock context and write `dm:web:<user ID>` audits.
   Resetting one member resets both members. Completed clocks require reset
   before editing; race selectors list only eligible unpaired clocks.
3. **Overview:** open the next tick, then close it to freeze inputs and queue
   durable resolution. Closing asks for browser confirmation. All live clock
   management locks during resolution/review, including requests from old tabs.
4. Use **Refresh status** to inspect resolution jobs and reveal the review link
   when processing finishes. This minimal console refreshes explicitly, not by
   polling. Retryable jobs automatically retry under Oban; discarded/cancelled
   processing requires diagnosed, authorized operator intervention (see
   [durable work](durable-work.md)). Raw worker exception payloads are not shown.
5. **Review:** inspect every frozen/resulting clock and source-labelled downstream
   consequence. A signed delta override replaces the clock's background delta
   for this tick; blank restores frozen behavior. Each edit requires an audit
   reason and recomputes from frozen inputs without changing live clock state.
   Completed frozen clocks cannot be overridden. Initial-full completion latches
   remain eligible even when their tick delta is lowered.
6. Edit public world news using blank-line-separated paragraphs (up to 100;
   each at most 2000 characters), or restore generated news. Empty narration
   suppresses news. Review history records actor, reason, and operation.
7. Inspect the **Exact public preview**, generated by ENG-8's shared delivery
   renderer. Hidden clock details and private notifications are omitted; known
   clocks show names only. Tick/clock logs elsewhere on this page are DM-only.
8. Confirm that you reviewed the current revision, then **Publish approved tick**.
   Approved live state, history, and outgoing delivery jobs commit atomically.
   You return to the overview; publication cannot be rolled back here.

Clock editors pass the loaded record to a comparison made under the domain's
campaign lock. Stale saves cannot overwrite another window's changes. Review
forms carry the approved draft UUID, not just a tick ID. Stale edits disable
editing/publication until explicit reload; stale publication attempts reload and
reset confirmation so the DM must inspect the current preview again. Domain
checks remain authoritative even if browser-disabled controls are bypassed.

## Quest turn review (ENG-20)

The same review page groups submitted turns by player. Inspect the pinned choice,
node transition, effective outcome, dice and final next choices. Reroll exactly one
die with a reason, choose a configured rolled outcome (or restore dice-derived),
and edit private player narration (blank restores authored text). Every accepted
edit recomputes all frozen consequences, preserving unrelated dice. Inspect both
**Exact public preview** and **Exact private preview**, including recipient IDs,
before confirmation/publication. The transaction applies quest progression,
flags, availability and world clocks together. See [quest-review.md](quest-review.md).

## Personal quest operations

**Characters** links players and manages typed facts. **Quests** assigns an
existing revision, replaces or ends a personal quest, and moves a character within
the pinned revision. Each actual quest intervention is audited and clears that
character's open choice. Stale editors and resolving/review locks are enforced
by the shared domain, not just disabled controls. See
[quest-operations.md](quest-operations.md) for the full operational checklist.
Use **Quest library & editor** to author fixed branching or cyclic quests. Save
incomplete copies, inspect the read-only directed graph, and select diagnostics
to repair broken start/destination links. Removing a referenced node asks for
confirmation and keeps broken references for repair; unreachable warnings do not
block release. Release appends immutable content; existing assignments stay pinned.
Imported rolled/conditional/effect-bearing choices remain opaque but all outcomes
are visible in the graph. See [quest-operations.md](quest-operations.md) for the
short authoring/recovery guide. Players run choices through normal Discord ticks,
not by editing the graph or assigning a quest.

## Character operating checklist (ENG-35)

1. Open **Characters**, select **Edit**, and inspect the Discord ID and connected
   journey: active pinned revision, node/status, and recent DM-only interventions.
   **Quest operations** opens this character; **Quest content** opens the library.
   Returning from quest operations keeps the selected profile.
2. Use **Edit** beside an existing fact; do not retype its key. Choose boolean,
   integer or string and explicit visibility. Strings are ordinary text, including
   quotes, not JSON. Hidden facts never appear in `/character`; visible facts are
   shown only to their owner. Audit reasons never appear in player replies.
3. Ownership changes (including unlinking to DM-controlled) require browser
   confirmation and clear that character's open submission. They do not replace
   its pinned quest or affect other players. A duplicate owner fails atomically.
4. Assign/replace/end/move in quest operations requires a reason and confirmation.
   Actual interventions clear only the selected character's open submission;
   moving to the same node is a no-op, moving to an ending completes it. Assigning
   the same released revision to two players creates independent assignments.
5. If another tab or published tick changed a profile/fact, saving or clearing
   is rejected, including changes away and back. Local inputs are not automatically
   retried. Reopen **Edit**, inspect persisted state, then deliberately reapply.
   Resolving/review locks still reject all character and quest mutations. Finish
   review/publication before retrying; content release does not repin assignments.

## Delivery failures

The overview shows the latest 50 outgoing delivery records and the latest eight
clock audits. Each failed/ambiguous delivery has its own retry form with an
optimistic generation check. Retrying one record never republishes state.
Ambiguous retry requires explicit confirmation that Discord was checked and that
a duplicate is acceptable. Sent/pending/sending records have no retry control.

## Published tick history (ENG-39)

Open **History** from the overview or review navigation. The list contains only
published ticks, newest first, in pages of 20. Open a publication to inspect its
publication time, selected draft/revision, frozen input identity, approved world
news, player results, recorded dice, and source-labelled before/after consequences.
Each detail section has independent pagination, also in pages of 20.

Review overrides show actor, reason, operation and previous/new draft IDs. Quest
interventions associated with that tick and publication clock audits have separate
sections: this is not a complete audit of every character or administrative edit.
Historical names come only from saved payloads; absent names use stable IDs or an
explicit missing-label fallback. Later content releases, character edits and live
clock changes cannot change the displayed approved content.

**Stored outgoing messages** shows the exact saved publication content, audience,
recipient, character/route when recorded, and chunk order. Opening prompts and
manual reminders are not publication messages. Delivery status is labelled as
**current**, not immutable history; raw exceptions and delivery guard data are not
shown. Follow **Existing delivery retry controls** to the overview for authorized,
generation-checked retries and explicit ambiguous-send confirmation. History
itself has no mutation, republish, delete or rollback controls. Reopen history to
refresh delivery status without rewriting approved content.

### Disposable-campaign verification checklist

1. Publish two development ticks; include a quest narration override and an
   assignment/move while a tick is open. Open each history entry and trace review
   revisions, intervention reasons and clock-effect sources independently.
2. Change live character names/flags, clock names/fills and released quest content.
   Reopen the first publication; saved results, names, IDs and messages must stay
   unchanged. Check a legacy world-only entry and missing-label fallbacks.
3. Fail a private delivery using a fake adapter (or disposable Discord account),
   inspect the current status, retry only that record through overview controls,
   then reopen history. Only delivery status/attempts should change.
4. Verify list/detail pagination and reject foreign/nonpublished tick IDs. Sign
   out, revoke/expire the session, or change the configured DM; history must no
   longer be accessible. Never use production credentials for this checklist.

These screens are the playable administrator, not an advanced graph editor or
complete administration audit. Gameplay Discord commands remain ENG-10. The console
uses streams for displayed collections, shared core input/icon components,
accessible labelled forms, keyboard focus styles, and reduced-motion-aware UI.
